# دفاتر المحاسب — نظام إدارة مكتب المحاسبة والمراجعة المتكامل

نظام محلي متكامل لإدارة مكتب المحاسبة والمراجعة، مبني ليعمل على جهاز مكتبك مباشرة:

- **إدارة مكتب المحاسبة**: شركات العملاء والمنشآت الفردية، كل شركة بملفها الضريبي الكامل بمواعيد التجديد، الالتزامات الضريبية بمواعيدها القانونية، المهام المُسندة للزملاء، ولوحة السكرتارية.
- **الشق المالي والمحاسبي**: فواتير البيع والشراء، العملاء والموردون، المخزون، الخزائن والبنوك، قيود اليومية ودليل الحسابات، الأصول الثابتة والإهلاك، الموظفون والرواتب، الموازنات، التقارير المالية والضرائب المصرية.
- **الأمان وحماية الجلسات**: حماية الخادم عبر بوابة Next.js Middleware (`src/middleware.ts`) والتحقق الموثوق من التوقيع الرقمي والصلاحيات على مستوى الأدوار (`admin`, `accountant`, `viewer`).

## خطوات التشغيل

1. تثبيت الحزم: `npm install`
2. إعداد البيئة: انسخ `.env.example` إلى `.env` وعدّل `SESSION_SECRET`
3. تهيئة قاعدة البيانات: `npm run db:push && npm run db:init`
4. تشغيل وضع التطوير: `npm run dev`

بيانات الدخول الافتراضية: `admin` / `admin123` — غيّرها من صفحة الإعدادات بعد أول دخول.

> ملاحظة عن مسار قاعدة البيانات: Prisma يحل مسارات `file:` النسبية بالنسبة لمجلد
> `prisma/` لا لجذر المشروع، لذلك `DATABASE_URL="file:../db/app.db"` هو ما ينتج
> الملف في `db/app.db` على جذر المشروع (وهو المسار المستثنى في `.gitignore`).

### طبقتان للقراءة والكتابة

- **القراءة**: صفحات Server Components تقرأ Prisma مباشرة (بلا طبقة API زائدة).
- **الكتابة**: كل التعديلات تمر عبر `/api/*` التي يحرسها `src/middleware.ts`، ثم يعود
  الصفحة للتحديث عبر `router.refresh()`.

هذا الفصل مقصود: بوابة الأمان التي بُنيت في `middleware.ts` تغطي كل طلب كتابة، فلا تمرّ
أي عملية تعديل عبر مسار لا يمر بالبوابة.

## العمود الفقري: سجل الأحداث والأتمتة

كل تغيير في النظام يمرّ عبر سجل أحداث **مشفّر السلسلة**: كل حدث يحمل تجزئة
SHA-256 تربطه بالحدث السابق. تعديل أي سجل في الماضي يكسر السلسلة، و
`verifyChain()` يكتشف الموضع بالضبط. هذا ما يجعل «100% قابل للتتبع» قابلًا
للتحقق، لا مجرد وعد.

```
أي كتابة ──► auditLog() ──┬──► AuditLog   (عرض سريع)
                          └──► EventLog   (سلسلة مشفّرة + إطلاق القواعد)
                                                 │
                                                 ▼
                                          قواعد الأتمتة
                                                 │
                                                 ▼
                                    طابور دائم في قاعدة البيانات
                                    (إعادة محاولة، تكرار آمن، تعثّر)
                                                 │
                                                 ▼
                                       عامل تنفيذ واحد
```

**لماذا طابور في القاعدة وليس مؤقّتًا في الذاكرة:** المهمة لا تضيع عند إغلاق
الجهاز. ولكل مهمة إعادة محاولة تصاعدية ومفتاح تكرار يمنع تنفيذ نفس العمل مرتين
وحالة «متعثّرة» تتحوّل إلى تنبيه بدل أن تضيع صامتة.

**لماذا عامل تنفيذ واحد:** التنفيذ المتوازي يجعل ترتيب الأحداث غير متوقع، ومكتب
محاسبي يحتاج ترتيبًا معلومًا. الدائرة تُشغَّل من `/api/automation/tick` — أي
cron خارجي أو فتح لوحة التحكم يكفي، فلا حاجة لعملية دائمة.

### التشغيل الآلي الحالي

| القاعدة | التوقيت | ما تفعله |
|---|---|---|
| `obligation.prepare_tasks` | عند تسجيل التزام | تنشئ مهمة التجهيز قبل الموعد بأسبوعين |
| `engagement.checklist` | عند إنشاء ملف عمل | تولّد المهام من قوالب الخدمة |
| `scan.sla_breaches` | كل 15 دقيقة | تنبّه على المهام المتأخرة |
| `scan.deadlines` | كل 30 دقيقة | تنبّه على الاستحقاقات القادمة |
| `ledger.trial_balance` | كل ساعة | تنبّه إن اختلف ميزان المراجعة |
| `audit.chain` | 2:00 صباحًا | تكشف أي عبث بسجل الأحداث |

كل مهمة مولّدة تحمل `templateCode` و`autoGenerated`، فإعادة تشغيل المعالج لا
تُنتج نسخًا مكررة، وسؤال «لماذا وُجدت هذه المهمة؟» له جواب مسجَّل.

### حدود الأتمتة — مقصودة

الترحيل إلى قيود اليومية والإقرارات الضريبية **لا** تُنفَّذ بلا مراجعة بشرية.
السبب قانوني لا تقني: القوائم والإقرارات تحمل توقيع محاسب مرخَّص، والمراجع
يسأل عن Person المسئول. النظام يجهّز ويصنّف ويكشف التعارضات، ثم يقف عند
بوابة الموافقة. ما يُؤتمت بالكامل هو العمل الكتابي: التنبيه، الإسناد، التوليد،
المطابقة، والوسم.

## حالة التنفيذ

**جاهز:** تسجيل الدخول والخروج وتغيير كلمة المرور · بوابة الأدوار · لوحة التحكم ·
شركات العملاء (قائمة + ملف كامل بالالتزامات والمهام) · الالتزامات الضريبية · المهام ·
دليل الحسابات · فواتير البيع والشراء (بسطور ومحرر أسطر وترحيل) · قيود اليومية مع العكس ·
التقارير (ميزان المراجعة، قائمة الدخل، المركز المالي، الذمم، ملخص القيمة المضافة) ·
مكتبة الواجهة · محرك الحسابات والتقارير.

**مخطط له (النماذج والـ API جاهزة، الشاشات قيد البناء):** إدارة ملفات العمل (Engagements) كشاشة · رفع الوثائق واستخراج بياناتها · أطراف الحساب · الخزائن
والبنوك · التحصيل والدفع · المخزون · الأصول الثابتة · الموظفون والرواتب · الموازنات ·
الإعدادات والنسخ الاحتياطي.

الشاشات غير المنجزة بعد تظهر في القائمة الجانبية معطّلة بعلامة «قريبًا» بدل روابط مكسورة.

## الفحص قبل الاعتماد

```bash
npm run check
```

```bash
npm run check          # الاستيرادات وحقول Prisma وتوجيهات use client
npm run check:schema   # بنية المخطط: العلاقات والأطراف العكسية والحقول المكررة
```

الأول يتأكد أن كل رمز مستورد مُصدَّر فعلًا، وأن كل حقل Prisma مستخدم موجود فعلًا
في المخطط، وأن كل ملف يستخدم الـ hooks يحمل توجيه `use client`. الثاني يتحقق من
أن لكل علاقة طرف عكسي — وهو الشرط الذي يرفض Prisma بسببه الملف.

كلا الفحصين مُختبَرagainst أخطاء مقحمة عمدًا، لأن فاحصًا يمر دائمًا بلا كاشف.

## ملاحظات معمارية مهمة

- **المبالغ من نوع `Float`**: هذا هو المخطط الأصلي في المشروع. كل عمليات الضرب والجمع
  تمر عبر `round2` في `src/lib/money.ts` لتقريب لخانتين، مما يقلل تراكم أخطاء الفاصلة
  العائمة. التحويل إلى `Decimal` هو التوصية الأولى للتحويل، لكنه تغيير في نوع
  الحقول وسيحتاج خطة ترحيل للبيانات الموجودة.
- **بيانات التهيئة في `seed-data.json`**: تستخدمه واجهة التطبيق وسكربت التهيئة معًا حتى
  لا تتكرر البيانات في مكانين. عدّل المصدر ثم شغّل `npm run db:init`.
- **ترقيم المستندات داخل معاملة**: `generateNumber` في `src/lib/accounting/api.ts` يزيد
  التسلسل داخل `$transaction` حتى لا يتكرر الرقم عند وجود طلبين متزامنين.
- **`SESSION_SECRET` الاحتياطي معروف ومكتوب في الكود**: مناسب للتشغيل المحلي فقط. أي
  استخدام حقيقي يجب أن يضبطه في `.env`.
